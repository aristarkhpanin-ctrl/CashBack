# Дорожная карта развития — фазы 15–27

Проект построен в 14 фаз (см. `PLAN.md`). Документ состоит из двух частей:
**Часть I (фазы 15–20)** — уже выполнена, доводит первичный функционал до
прод-контура. **Часть II (фазы 21–27)** — интеграция дизайн-handoff
`Cashback(4).zip` (`design_handoff_cashback_admin`): формализованный контракт
`API.md` фиксирует функциональность за уже существующими экранами; Часть II
закрывает дельту между этим контрактом и текущим кодом.

Каждая фаза самодостаточна: её можно выполнять и демонстрировать отдельно,
порядок ниже — рекомендуемый, но жёсткая зависимость помечена явно.

**Текущее состояние (после фазы 14 + доводки функционала):** фронтенд работает
в двух режимах (`LIVE API` / `ДЕМО-ДАННЫЕ`), кампании имеют полный CRUD через
FSM, аналитика (воронка, матрица сегмент×категория) и SHAP-объяснения читаются
из бэкенда. Модельными (демо) остаются: график динамики на дашборде, вкладка
каналов, страницы «ML-лимиты» и «Пользователи» (локальный стейт), список
A/B-экспериментов (нет эндпоинта листинга).

## Фаза 15 — Аутентификация и RBAC ✅ выполнена

> Итог реализации: миграция получила номер **002** (003 был занят в плане
> ошибочно — после 001 других не существовало); JWT — python-jose + bcrypt,
> пароли демо-стенда предвычислены в миграции/сидере. Отклонение от плана:
> прокидывание JWT в recommendation_api и mobile_api ВЫПОЛНЕНО отдельной
> beyond-plan задачей: rec_api требует service|access-токен (общий
> HS256-секрет), mobile_api минтит короткоживущий service-токен для
> upstream-вызовов, фронтовый admin-токен принимается для live-SHAP.
> Матрица прав на странице «Пользователи» осталась статической (роль →
> права зашиты на сервере), как и планировалось.

### Цель
Заменить клиентский переключатель ролей на реальную аутентификацию:
JWT-логин, роли admin / marketer / analyst, серверная проверка прав на
мутирующих эндпоинтах.

### Обоснование решения
Сейчас все API открыты: любой, кто видит Swagger, может активировать кампанию
или изменить бюджет. Для банковского продукта это неприемлемо и это первый
вопрос на защите.

Выбор — **JWT (python-jose) поверх собственной таблицы `admin_users`**, а не
Keycloak/OAuth2-провайдер, потому что: (а) стек демонстрационный, внешний IdP
добавил бы контейнер и сложность без прироста демонстрируемой компетенции;
(б) JWT-клеймы с ролью — ровно то, что нужно для RBAC-зависимости FastAPI;
(в) фронтенд уже структурирован вокруг ролей (`PERMISSIONS` в mockData), их
серверный аналог ложится 1:1. Access-токен 15 мин + refresh 7 дней — стандарт,
достаточный для демо и корректный для прода.

### Декомпозиция
1. **Миграция `003_admin_users.py`** — таблица `admin_users(user_id UUID PK,
   email UNIQUE, password_hash, full_name, role admin_role_enum, created_at,
   last_login_at)`; ENUM `admin_role ('ADMIN','MARKETER','ANALYST')`. Сид трёх
   пользователей в `scripts/seed_demo_data.py` (пароли через `bcrypt`).
2. **Auth-роутер в campaign_manager** (`app/api/auth.py`):
   `POST /auth/login` (email+password → access+refresh), `POST /auth/refresh`,
   `GET /auth/me`. Схемы в `app/schemas.py`, настройки (`jwt_secret`,
   `access_ttl`) в `app/config.py` + `.env.example`.
3. **Зависимости прав** (`app/security.py`): `get_current_user` (декодирование
   Bearer-токена) и фабрика `require_role("ADMIN", ...)`. Матрица:
   - `POST/PATCH /campaigns*` — ADMIN, MARKETER;
   - `DELETE`-действий нет (осознанно, аудит);
   - `/experiments*` мутации — ADMIN;
   - `GET`-эндпоинты — любой аутентифицированный;
   - `/health/*`, `/metrics` — без токена (k8s-пробы).
4. **Прокидывание в recommendation_api и mobile_bff** — общий модуль проверки
   JWT скопировать в `services/*/app/security.py` (сознательное дублирование:
   сервисы не имеют общего пакета, это зафиксировано в ADR-0002); mobile_bff
   использует отдельный клеймовый тип `client` (мобильный клиент ≠ админ).
5. **Фронтенд**: страница логина (`components/cashback/pages/Login.tsx`),
   хранение токена в памяти + refresh в httpOnly-cookie недоступен без
   бэкенд-сессий, поэтому: access в памяти, refresh в `localStorage` с
   пометкой в README про XSS-компромисс демо-стенда; axios-интерцептор
   `Authorization: Bearer` + авто-refresh по 401; `currentUser` берётся из
   `GET /auth/me`, переключатель ролей остаётся только в демо-режиме.
6. **Страница «Пользователи» → live**: `GET/POST/PATCH /auth/users` (ADMIN),
   смена роли пишется в БД; матрица прав остаётся статической (роль → права
   захардкожены на сервере) — динамическая матрица прав в БД отклонена как
   overkill для трёх ролей.
7. **Тесты**: unit на `require_role` (403/401), integration «login → создать
   кампанию → 201; аналитик → 403», обновить существующие интеграционные
   тесты (фикстура токена).

### Критерии приёмки
- Без токена мутирующие эндпоинты возвращают 401, с ролью ANALYST — 403.
- Логин на фронтенде работает в live-режиме; демо-режим не требует логина.
- `make test` зелёный; в Swagger появилась кнопка Authorize.

Оценка: ~2–3 дня. Риск: миграция ломает существующие интеграционные тесты —
закладывать время на их обновление (шаг 7).

## Фаза 16 — Достройка аналитики: trend, channels, A/B-страница ✅ выполнена

> Итог реализации: миграция получила номер **003** (002 занят admin_users
> из фазы 15). Канал доставки — ENUM `delivery_channel`
> (PUSH/SMS/EMAIL/IN_APP), зеркалит адаптеры NotificationPipeline.
> Маппинг децилей в 5 корзин вынесен в `app/segments.py` (бэкенд) с
> перекрёстной ссылкой на `adapters.ts` (фронтенд). Страница
> «Эксперименты» добавлена в новый дизайн (список, z-тест, start/stop,
> создание A/B 50/50); в демо-режиме — статичные mock-результаты.
> Дашборд рисует live-тренд по 5 корзинам, вкладка каналов читает
> /analytics/channels.

### Цель
Убрать последние демо-заглушки UI: график динамики, канальная аналитика,
список A/B-экспериментов.

### Обоснование решения
В `recommendations` сейчас нет ни времени отклика, ни канала доставки —
есть только `generated_at` и `response_status`. Считать «динамику принятых»
по `generated_at` можно, но это дата генерации, а не принятия — кривая будет
смещена. Правильное решение — **добавить колонки `responded_at` и `channel`**
миграцией, а не выводить приближение: (а) это честные данные для дальнейшего
OST (optimal send time) из главы 3.2; (б) миграция тривиальна; (в) канал уже
известен в момент respond-вызова mobile_bff — его просто негде было хранить.

Для A/B-списка: фронтовый `abApi.list()` уже написан и бьёт в `GET
/experiments`, которого нет (сервер отвечает 405). Добавляем эндпоинт, а не
переписываем фронт — компоненты `ZTestCalculator`, `VariantComparisonTable`,
`SignificanceBadge` из первого дизайна лежат в `features/ab-testing/ui/`
рабочими и неиспользуемыми, их нужно только обернуть в страницу нового дизайна.

### Декомпозиция
1. **Миграция `002_recommendations_response_meta.py`**: `ALTER TABLE
   recommendations ADD COLUMN responded_at TIMESTAMPTZ NULL, ADD COLUMN
   channel channel_type NULL`; индекс `(responded_at)` частичный
   `WHERE response_status = 'ACCEPTED'`. Backfill в сидере: у принятых
   рекомендаций `responded_at = generated_at + random(1м..48ч)`, канал —
   взвешенный выбор.
2. **mobile_bff**: `POST /v1/mobile/recommendations/{id}/respond` пишет
   `responded_at = now()` и `channel` (новое опциональное поле тела запроса,
   по умолчанию `MOBILE`).
3. **`GET /analytics/daily-trend`** (campaign_manager): параметры
   `campaign_id?`, `period=30`, `bucket=day`; ответ
   `[{date, segment_bucket, accepted}]`, где `segment_bucket` — те же 5 корзин
   децилей, что использует фронтенд (маппинг вынести в `app/segments.py`,
   зеркально `frontend/src/shared/api/adapters.ts`; несоответствие корзин —
   единственная точка рассинхрона, поэтому оба файла получают перекрёстный
   комментарий).
4. **`GET /analytics/channels`**: `[{channel, sent, opened, converted}]`;
   sent = все рекомендации канала, opened = `response_status != 'PENDING'`,
   converted = `ACCEPTED` (семантика зафиксирована в docstring — «open»
   в пуш-канале это факт реакции, не delivery receipt).
5. **`GET /experiments`** (список, пагинация `limit/offset`, сортировка по
   `start_date DESC`) + фронтовые типы уже готовы.
6. **Фронтенд**: хуки `useLiveTrend`, `useLiveChannels` в `shared/api/live.ts`
   + адаптеры; Dashboard/TrendChart и ChannelsView переключаются на live с
   fallback на текущие генераторы (паттерн уже отработан на воронке);
   снять баннер «канальная аналитика не подключена». Новая страница
   `pages/Experiments.tsx` (список + результаты + z-тест), пункт сайдбара
   `perm: analytics`.
7. **Тесты**: integration на три новых эндпоинта (сид фикстурами), unit на
   агрегацию корзин.

### Критерии приёмки
- В live-режиме дашборд и вкладка каналов не содержат ни одного
  сгенерированного числа; бейдж «модельная динамика (демо)» удалён.
- Страница «Эксперименты» показывает список из БД и p-value из
  `/experiments/{id}/results`.

Оценка: ~2–3 дня. Зависимость: если фаза 15 сделана раньше — новые эндпоинты
сразу закрываются `require_role`.

## Фаза 17 — Надёжность fintech-контура ✅ выполнена

> Итог реализации: базовый тест идемпотентности уже существовал —
> он расширен проверками «Kafka publish ровно один раз» и «ровно одна
> строка аккрула»; добавлены тесты гонки за бюджет (параллельные
> начисления и параллельные `budget/check`); метрика
> `campaign_budget_utilization_ratio` экспортируется планировщиком;
> observability-стек — `docker-compose.observability.yml` (`make up-obs`).

### Цель
Доказать (тестами и алертами), что денежный контур переживает повторную
доставку сообщений и деградацию инфраструктуры.

### Обоснование решения
Идемпотентность начисления **уже реализована** (уникальный констрейнт
`uq_accrual_transaction_campaign` + `ON CONFLICT DO NOTHING` в
`transaction_listener/app/accrual/engine.py`), но не покрыта тестом — а это
единственная гарантия против двойного списания при Kafka rebalance. Тест
дешевле и важнее любого нового кода. Отдельно проверяется тонкое место:
повторная доставка не должна повторно инкрементить `budget_spent` — вставка
аккрула и обновление бюджета обязаны быть в одной транзакции, и тест должен
это зафиксировать.

Алертинг выбран через **Prometheus rules + Alertmanager в compose-стеке**,
без внешних SaaS: метрики уже экспортируются всеми сервисами, недостаёт только
правил и визуализации. Grafana добавляется как готовый provisioned-дашборд
(JSON в репозитории) — воспроизводимо из коробки, без ручной настройки.

### Декомпозиция
1. **Тест идемпотентности** (`services/transaction_listener/tests/integration/
   test_accrual_idempotency.py`): дважды подать одно `transaction_event` →
   один аккрул, `budget_spent` увеличен один раз, Kafka-событие `accrual.paid`
   отправлено один раз (мок-продьюсер).
2. **Тест конкурентного резервирования бюджета**: два параллельных
   `POST /campaigns/{id}/budget/check` на остаток < суммы двух заявок →
   ровно один `reserved=true` (проверяет `SELECT … FOR UPDATE`).
3. **Prometheus rules** (`infrastructure/prometheus/alerts.yml`):
   - `KafkaConsumerLagHigh`: lag > 10 000 за 5 мин;
   - `RecommendationLatencyHigh`: p95 > 100 мс за 5 мин;
   - `CampaignBudgetNearlyExhausted`: budget_spent / budget_total > 0.95;
   - `ModelDriftDetected`: last_psi > 0.2 (метрику публикует ml_training);
   - `ServiceDown`: up == 0 за 2 мин.
4. **Alertmanager** в `docker-compose.yml` (роут в webhook-заглушку/лог) +
   **Grafana** с provisioned-дашбордом: RPS/latency сервисов, consumer lag,
   бюджеты кампаний, PSI. JSON — `infrastructure/grafana/dashboards/`.
5. **README**: раздел «Наблюдаемость» с портами и скриншотом.

### Критерии приёмки
- Оба новых интеграционных теста зелёные в CI.
- `docker compose up` поднимает Grafana с готовым дашбордом; остановка
  recommendation_api приводит к алерту ServiceDown в Alertmanager UI.

Оценка: ~1–2 дня. Ни от чего не зависит, максимальное отношение
ценность/усилия — делать первой.

## Фаза 18 — ML-контур 2.0 ✅ выполнена

> Итог реализации и отклонения от плана:
> * **R7 (MlRateCap)** читает только Redis-снапшот `ml_limits:snapshot`
>   (без Postgres на горячем пути); снапшот публикует campaign_manager
>   при PUT /ml-limits и на каждом тике планировщика. `daily_budget` и
>   `auto_approve` — управленческие атрибуты, в R7 не применяются
>   (сквозной дневной счётчик расходов по корзине — отдельная задача).
> * **PSI считается по квантильным сводкам** (`feature_quantiles.json`,
>   101 перцентиль на признак, логируется тренером) — прежний гейт
>   сравнивал пустые схемы и фактически не работал; теперь PSI реален
>   и публикуется в **Pushgateway** (ml_training — one-shot CLI, его
>   нельзя скрейпить).
> * **Онлайн-CTR атрибуцируется по model_version** (миграция 005 +
>   персист версии в recommendations): gauge `ml_online_ctr{model_version}`
>   в campaign_manager. **Синхронный holdout ДОБАВЛЕН** отдельной
>   beyond-plan задачей: ModelWatcher держит Production + предыдущую
>   (Archived) модель, ~5% пользователей детерминированно (md5-хеш)
>   обслуживаются предшественником, model_version в ответе отражает
>   реально применённую модель → две версии естественно разделяются в
>   gauge. Нет предшественника → все на Production (деградация).
> * `feature_values` добавлены в RecommendationItem — waterfall в UI
>   показывает и вклад, и сырое значение признака.

### Цель
Три улучшения ML-истории: онлайн-метрики продовой модели, управление
ML-лимитами из UI с применением в BRE, полные SHAP-объяснения со значениями
признаков.

### Обоснование решения
**Онлайн-метрики.** Двухусловный критерий продвижения (ΔAUC ≥ 0.005 ∧ PSI ≤
0.2) — офлайн-критерий; он не ловит ситуацию «офлайн-метрики выросли,
фактический CTR упал». Решение — ежедневный Airflow-таск, считающий
фактический CTR/acceptance rate рекомендаций по `model_version` и пишущий их
в MLflow как метрики продового рана. Holdout-группа (5% пользователей получают
рекомендации попsavedной модели-предшественника) даёт честный uplift; выбор
через детерминированное хеширование `user_id` — переиспользуется механика
A/B-модуля.

**ML-лимиты.** Страница «ML-лимиты» сейчас пишет в localStorage — красивая,
но неотчуждаемая от браузера. Перенос в БД превращает её в реальный контур
управления: бизнес задаёт максимальную ставку на сегмент, BRE применяет её как
правило. Реализация — правило R7 в существующей Chain of Responsibility
(`recommendation_api/app/bre/rules/ml_rate_cap.py`), читающее лимиты из Redis
(кэш таблицы, TTL 60 с) — это соответствует архитектуре остальных правил
(например, budget_reservation тоже ходит во внешнее состояние).

**Значения признаков в SHAP.** Сейчас API отдаёт только вклады
(`top_factors`), колонка «значение» в waterfall пуста. Значения признаков уже
лежат в Redis (`features:{user_id}`) и загружаются при ранжировании — их
нужно только включить в ответ. Расширение схемы обратно совместимо
(новое поле `feature_values`).

### Декомпозиция
1. Миграция `004_ml_limits.py`: `ml_limits(segment_bucket PK, min_rate,
   max_rate, daily_budget, auto_approve, risk_level, updated_by, updated_at)`
   + сид дефолтов.
2. campaign_manager: `GET/PUT /ml-limits` (PUT — ADMIN, фаза 15), аудит в
   `audit_log`.
3. recommendation_api: правило `R7_MlRateCap` (ставка рекомендации >
   max_rate сегмента → скорректировать до cap; daily_budget исчерпан →
   REJECT) + Redis-кэш лимитов + unit-тесты по образцу `test_bre.py`.
4. Фронтенд: `MlLimits.tsx` переводится на `useQuery/useMutation` с fallback
   на localStorage в демо-режиме (паттерн ops из Campaigns).
5. recommendation_api: `feature_values: dict[str, float]` в
   `RecommendationItem` (top-5 признаков из уже загруженного вектора);
   фронтовый адаптер `explanationFromApi` заполняет колонку «значение»

6. ml_training: таск `compute_online_metrics` в DAG `ml_retrain_pipeline`

7. Holdout: поле `serving_group` (`prod`/`holdout`) в ответе рекомендаций +

### Критерии приёмки

Сделать матрицу прав редактируемой: таблица `role_permissions`,

### Обоснование решения

полный.

### Обоснование решения
README прямо перечисляет прототипные артефакты, недопустимые в проде.
Основные ещё присутствуют: демо-переключатель ролей в `TopBar` живёт рядом с

emoji-иконки (📢👥💸🎯 и в MCC-плитках) не заменены на SVG. Это фаза
«последней мили» — косметика с реальным весом на защите (визуальная зрелость).

Пустые состояния завязаны на pending-контракт фазы 24: жёлтые баннеры
«ожидание данных» и «—» в live должны гейтиться серверными флагами, а не
клиентской эвристикой.

### Декомпозиция
1. `Layout.tsx`: демо-переключатель ролей рендерится только в демо-режиме
   (`!isLive`); в live — профиль-меню (имя, роль, «Выйти»).
2. Иконки: пакет Lucide (уже допустимо офлайн — tree-shake), маппинг
   `icon-name → компонент` (сервер отдаёт имя из фазы 21); stroke 1.5–1.8,
   18px, как в сайдбаре. Замена emoji в KPI-карточках, MCC-плитках,
   инсайт-карточках.
3. Пустые состояния live: баннеры и «—» по серверному `pending` (фаза 24);
   единообразные toasts после мутаций.
4. Тесты: Playwright — в live нет демо-переключателя; 0 console-ошибок;
   snapshot ключевых экранов (визуальная регрессия по желанию).

### Критерии приёмки
- В live-режиме демо-переключатель ролей отсутствует.
- Ни одной emoji-иконки в UI (единый SVG-сет).
- Пустые состояния в live управляются серверными флагами.
